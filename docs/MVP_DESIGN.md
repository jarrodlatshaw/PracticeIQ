## Data and schema design

Preserve the existing `medical_practices` table and its text `practice_id` as the practice identity anchor. New functionality may use an isolated `practiceiq` schema pending integration; avoid duplicating or replacing existing practice, taxonomy, and Census data. Datasets have release, period, source URI/license, checksum, imported time, coverage, suppression, and load state. Providers keyed by validated NPI have names/taxonomies and source versions. Locations have address, lat/lon, optional PostGIS geography, and geocoding provenance. Practices have identity and primary location. Provider-practice affiliations have effective dates, evidence, and confidence; only reviewed or high-confidence, non-conflicting affiliations are used for aggregations. Never merge practices on name or address alone; exact organization NPI or authoritative affiliation can support a match. A name/address/phone match is a review candidate, not an automatic merge. Specialty compatibility is an explicit reviewed crosswalk, versioned by service line.

Referral edges are keyed by release, source NPI and destination NPI, with counts, waits, suppression and provenance. Unresolved NPIs remain staged; don't silently drop them. Separate periods and direction conventions; never sum releases together. Use staging, validate schema and license, stream rows, quarantine rejects with line numbers, detect duplicate keys, reconcile counts and atomically promote a complete batch. Reimport is idempotent by source checksum and release. No source data or credentials in Git. Suppressed or missing values stay null, not zero.

CMS utilization stores NPI, year, geography, specialty, HCPCS, allowed/payment amounts and beneficiaries, preserving source definitions and suppression. Benchmarks retain source, year, cohort, denominator, population and derivation. Derive a cohort's Medicare allowed amounts per unique beneficiary only from a CMS file whose denominator is truly unique at that level; summed HCPCS beneficiaries are not unique. Use a minimum cohort size, geographic/specialty fallback, robust distributions, and expose the benchmark as a Medicare proxy, not actual collections. Client-specific collections per new patient for a matching period/service line can override with source and effective dates. Capacity and payer mix are future inputs; never infer them from Medicare aggregates.

Client practices, membership/tenant ACL, private financial metrics, configurable scenario assumptions, and scoring profiles are tenant scoped. Demographics store geography, ACS vintage, measure, denominator and uncertainty; do not sum overlapping geographies. Drive times are cached by origin/destination, mode, routing dataset/version and timestamp. OSRM may be unavailable; distance and drive time are separate, with null when missing. Use self-hosted OSRM for production and verify license/usage policy. Use indexed geography with ST_DWithin for radius searches, ordinary indexes for NPIs, periods and affiliations. Add materialized summaries only after actual data and query plans justify refresh and indexes.

## Calculations

Choose one data release and period, target specialty, client locations, and market radius. For each source NPI, restrict edges to destination NPIs in the target specialty and market, using reviewed affiliations. Current capture is the sum of qualifying edge counts to client providers; competitor flow is the sum to qualifying non-client providers. Observed flow is their sum and leakage is observed minus captured. These are **edge-count sums**, not deduplicated patients: a patient may appear in multiple edges and suppressed edges are absent. They are proxy relationship volume, not verified referrals or unique new patients. Unknown direction, incomplete affiliations, suppression, outside market and missing locations must be disclosed; do not treat missing data as zero.

Low/base/high incremental edge-volume equivalents = leakage × configured low/base/high capture rate; revenue scenario = incremental equivalents × configured collections per incremental patient. Estimates depend on assuming edge-volume equivalents approximate incremental patients; label that assumption and do not combine incomparable periods or claim precision. No benchmark means null revenue. Report both components and parameters, periods and coverage. Default 5%, 10%, 15% are illustrative, not validated predictions. Existing observed capture must not exceed observed flow. Do not sum opportunities as unique patients or revenue without an overlap adjustment.

Score 0–100 via a versioned weighted mean of available, normalized components (flow, leakage, distance, drive time, specialty fit, competitor concentration, revenue, size, concentration, demand, supply). Store weights, normalization bounds, values, component scores, availability and as-of data. Renormalize only if a configured minimum weight coverage is met; otherwise null score. Avoid treating unknowns as zero. Ranking and thresholds need calibration against outcomes.

## Lovable contracts (planned, not implemented)

All RPCs require an authenticated user authorized for the requested practice; enforce RLS/explicit membership checks on every path. Use explicit output columns, stable pagination and snapshot identifiers. Errors distinguish unauthorized, unknown practice, data unavailable, invalid parameters and stale release. Common metadata: release/period, as-of, geography, assumptions, suppression/coverage and limitations. Coordinates are WGS84 longitude/latitude and nullable. Financial data is never exposed across tenants.

- `get_market_overview(practice_id)`: competitor_count, provider_count, population, demand/supply measures and definitions, market opportunity, geography, metadata.
- `get_referral_opportunities(practice_id)`: source NPI/name/specialty/practice, coordinates, distance and drive time, observed/captured/leakage edge-volume, score and component scores, low/base/high revenue, assumptions and confidence. Paginate and filter server-side.
- `get_referral_network(practice_id)`: nodes (NPI, name, affiliation, specialty, coordinates), edges (source, destination, count, period, suppression), metadata.
- `get_referral_leakage(practice_id)`: source and competitor destination, edge volume, confidence, geography, period and caveats.
- `get_top_competitors(practice_id)`: destination practice, flow, locations and source/period coverage.
- `get_revenue_opportunity(practice_id)`: scenarios and assumptions, benchmark basis, and explicit non-additivity/overlap limitation.
- `get_provider_detail(npi)`: identity, affiliations with confidence and effective dates, specialties, locations, source provenance and permitted network metrics, subject to practice access.

Lovable screens: market map/overview, opportunity ranked table with component explanations, network graph, leakage and competitor tables, provider detail, assumptions and benchmark provenance. Filters: period/release, radius, specialty, score, volume, scenario; map layers: practices, competitors, sources, demand geography, patient-sharing edges. Charts must label counts as shared-patient edge sums. Handle loading, empty, suppressed, missing geocodes, stale/unavailable datasets, authorization and errors distinctly. Never expose raw private financial records or licensed data without policy review.

## Proposed relation dictionary and integrity rules

The following are proposed relations, not existing or deployed tables. UUID identifiers are local surrogate keys; all source identifiers remain separately available. Foreign keys, unique constraints, provenance and effective dates apply to every imported entity.

| Relation | Primary columns and constraints | Purpose |
| --- | --- | --- |
| `dataset_releases` | id, source, version, period_start/end, sha256, license_ref, coverage, suppression_rule, status, loaded_at; unique source/version/hash | Reproducibility and release selection |
| `providers` | npi char(10) PK, display_name, entity_type, source_release_id | Identity only, not practice ownership |
| `specialty_taxonomy_map` (existing) | taxonomy_code, display_group, confidence, review_note; verify constraints | Reuse existing specialty mapping |
| `provider_specialties` | npi, specialty_id, effective dates, source_release_id | Multiple taxonomies and history |
| `locations` | id, address fields, lat/lon, geography point, geocode source/date | Map and radius filtering |
| `medical_practices` (existing) | text practice_id and observed fields above | Preserve existing practice identity; any supplemental resolution uses practice_id |
| `provider_practice_affiliations` | provider_npi, practice_id, location_id, effective dates, evidence, confidence, reviewed_at | Avoid unsupported or stale assignments |
| `referral_edges` | release_id, from_npi, to_npi, patient_count, transaction_count, mean/std wait, suppression flag; unique release/from/to | Shared-patient relationships in a specific release |
| `specialty_compatibility` | source_specialty, destination_specialty/service_line, version, approved | Define eligible destinations and explain compatibility |
| `cms_utilization` | release_id, npi, year, geography, specialty, hcpcs, beneficiaries, allowed_amount, payment_amount, suppression | Source-specific facts with valid denominator definitions |
| `revenue_benchmarks` | id, year, specialty, geography, basis, allowed_per_beneficiary, cohort_count, uncertainty, release_id | Transparent proxy inputs, never actual collections |
| `census_demographics` (existing) | geoid and observed demographic/geography fields; verify complete schema and vintage | Reuse existing demand inputs; supplement provenance where missing |
| `drive_times` | origin_location_id, destination_location_id, routing_mode, graph_version, seconds, distance_meters, calculated_at | Cached route results with freshness |
| `client_practices` | id, tenant_id, practice_id, primary service line, active | Client context; tenant scoped |
| `client_financial_metrics` | client_practice_id, service_line, period, collections, new_patients, payer_mix, capacity, source | Private observed economics |
| `assumption_profiles` | client_practice_id, effective dates, radius, low/base/high capture, benchmark choice, score weights/version | Versioned reproducible choices |
| `referral_source_metrics` | snapshot_id, client_practice_id, source_npi, observed/captured/leakage, coverage and confidence | Derived, refreshable snapshot; raw edges remain authoritative |
| `opportunity_scores` | snapshot_id, source_npi, overall, components, weights, coverage, model_version | Explainable, reproducible ranking |
| `tenant_memberships` | tenant_id, user_id, role, active | Tenant authorization, enforced for all client data |

Use numeric checks for nonnegative counts, ordered assumptions and valid effective dates; enforce release compatibility. Composite indices on `(release_id, from_npi)`, `(release_id, to_npi)`, `(practice_id, provider_npi)` and GIST geography support representative joins. Supabase exposed functions should use invoker security and RLS by default, with no publicly accessible raw client data. A security-definer function, if unavoidable, must set a fixed search path, explicitly check membership and revoke public execution. The existing deployment's grants, schema exposure and RLS take precedence after review.

## Proposed import workflow

Receive each licensed file in private storage and record its checksum, licensed release, period and direction semantics. Validate a release-specific column mapping and units; stream to staging with batch/line identifiers. Reject malformed identifiers/counts and duplicate pair keys to quarantine without changing a published release. Record suppressed rows and unknown values explicitly. Resolve NPIs against the correct provider snapshot; report unresolved fractions and allow later reprocessing. Validate rows, counts, distribution, min/max dates, suppression and geographic coverage against the vendor manifest; require documented sign-off before transactionally promoting the complete release. Log import version, mapping, counts, failures, provenance and timestamp; retry the same release/hash without double counting. Implement bulk loading and partitioning only after testing realistic file sizes. The current staging script is an initial validation tool and does not yet implement the full workflow.
